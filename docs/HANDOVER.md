### 5.1b 三次扩图与"为什么必须扩到 220 列"

**第一次扩图（76×48 → 152×96）：治"算子挤"**。拥挤的根因是棋盘容量，不是摆法——
旧图 76×48 = 3,648 格，每格只能容 1 个单位，1192 营全入场时占格率 32.7%，怎么摆都挤；
原版 standard（52×32=1,664 格、122 算子）是 7.3%，那才是设计密度。

**第二次扩图（152×96 → 220×96）：治"地理失真"**。152 列时城镇坐标只能靠手估，
无法与真实经纬度对应。反解证明横向尺度差 2~4 倍（见 §5.3a），西部 46 座城镇被压到 c1。
加宽到 220 后，用真实经纬度 1:1 铺开：

| 阶段 | 棋盘 | 面积 | 全部 1192 营占格率 | 城镇数 |
|---|---|---|---|---|
| Phase 0 | 76 × 48 | 3,648 格 | 32.7% | 25 |
| 2026-10-12 | 152 × 96 | 14,592 格 | 8.2% | 88 → 349 |
| **2026-10-13（现行）** | **220 × 96** | **21,120 格** | **5.6%** | **436** |
| 参考：原版 standard | 52 × 32 | 1,664 格 | — | 25（122 算子，7.3%） |

**旧图重投影 = 旧图 ×2 平移 `[OFF_C, OFF_R]`**（`new = old*2 + [OFF_C,OFF_R]`，`OFF_C=4/OFF_R=4`），
旧图落在新图西侧带（c4..107）。项目尺度约定 **3 km/格（7.8 km²/格）** ⇒ 220×96 名义 **660×288 km**。

📌 **"1:1 铺开"的准确含义**：城镇坐标由真实经纬度**线性标定**得到
（51.2 列/度 ≈ 1.39 km/列），因此**相对方位与相对距离次序是正确的**（谁在谁东、大致远近）；
但它与"3 km/格"的名义格宽并不自洽——真实 4.4~8.68°E 只有约 304 km，
而 220 列按 3 km/格是 660 km。换句话说：**加宽换来的是"地理关系正确"，
不是"绝对比例尺吻合"**。若日后要求严格等比例，需同步调整格宽或列数，别只改地图尺寸。

⚠️ **重投影不是简单 ×2**：旧图自身横纵比例并不自洽，机械 ×2 会把德军艾费尔城镇
（普吕姆/比特堡/施塔特基尔/洛斯海姆）搬到**美军阵地背后**，导致德军开局 69% 断补。
2026-10-12 曾用"显式方位修正"打补丁；**2026-10-13 起改为整表按真实经纬度换算**（§5.3a），
这类补丁不再需要，但历史教训要记住：**任何坐标搬迁都必须用 `qa/supply_gap.js` 复验覆盖率**。

#### 5.4b 崎岖度：三级细节层（`mapgen.js` 的可选字段）

**问题**：大图上线后地形是"几十公里的大色块"，一眼看去很平滑。根因是噪声频率太粗——

## 8. 踩坑记录（必读，全部真实付出过代价）

1. **`DATA_BASE` 守卫事故（最重要）**：`ui.js startGame` 曾写成三元式 `DATA = (big && DATA_BIG) ? DATA_BIG : DATA_BASE`——而 `DATA_BASE` 只在 `data_big.js` 定义。**原版构建里它是 undefined → 原版成品开局必炸**（DATA 被置 undefined）。现已改为守卫形态：
   ```js
   if (scenarioId === 'big' && globalThis.DATA_BIG) globalThis.DATA = globalThis.DATA_BIG;
   else if (globalThis.DATA_BASE) globalThis.DATA = globalThis.DATA_BASE;
   ```
   **任何触碰 DATA 切换的改动都必须保证在"没有 data_big.js 的环境"里不炸**（原版与本项目的 js 已分家，但守卫写法仍是好习惯）。
2. **同一消息并行发多条 Edit 到同一文件会静默丢编辑**（真实发生：TOWNS.push 行丢失、index.html 注释行丢失）。**同文件编辑一律逐条串行**。
3. **无头 Chrome 同一实例第二次"导航+eval"会挂死**（SIGTERM，SwiftShader 环境复现多次）。**每拍一张重启干净 Chrome**；shot.js 必须带 `RELOAD=1`（否则复用旧页面目标，状态错乱）。
4. **shot.js 的 setup 表达式必须轮询等模态**（`new Promise + setInterval` 查 `.scen[data-id=big]`/`#mStart`），直接点会 `null.click`。双人热座要 skip 两次简报。长表达式用 `SETUP_FILE=<文件>` 传入（命令行传会被 shell 剥引号，本机实测过）。
5. **Bash shim 限制**：无 `ls/grep/cd`（偶发剥离 `cd` 前缀）——文件操作与跨目录命令一律 `node -e` 或 node 绝对路径调用（`check_big.js`/`shot.js` 都以 `__dirname` 定位 ROOT，绝对路径可跑）。
6. **断补排查方法论**：见 §5.3，工具在 `qa/supply_gap.js`（诊断 + 最优补点求解）。
7. **workbuddy 文件版本历史**在 `C:\Users\雷宇轩\.workbuddy\file-history\<会话ID>\<哈希>@vN`，可按字节数+SHA256 找回被覆盖前的文件（原版 mapgen.js 就是这么救回来的）。
8. **重投影地图时，"机械等比缩放"是个陷阱（2026-10-12 付过代价）**：旧图自身的横纵比例就不自洽（横向偏密、纵向偏挤），把旧图 ×2 平移后，德军艾费尔城镇（普吕姆/比特堡/施塔特基尔/洛斯海姆）会落到**美军阵地背后**——德军开局直接 69% 断补。必须按**史实方位**逐座校正这些城镇，再用 `qa/supply_gap.js` 验证覆盖率。同理：**地图面积扩大 N 倍后，补给城镇数量必须同步增加**（否则覆盖率崩到 30%），新增城镇要在前缘后方**均匀铺开**，不能只加在后方。
9. **散布器的两个隐形 bug（新写扇区布防时踩过）**：
   ① `placeSector(sector, 1, ...)` 逐个营调用会让"最小间距 ≥2"完全失效（每次只放 1 个，永远没有第二个来撞它）——必须**先按扇区分组、再整批铺设**；
   ② 聚合统计的包围盒初值写成 `{c0:99, r0:99}` 会把列也夹在 99、行夹在 99，导致诊断输出的坐标范围完全失真（看起来像"算子跑到图外"，其实没跑）。初值要用 `c0:999, r0:999` 或 `±Infinity`。
10. **算子"挤"要同时治两处**：布防分散（§6 扇区）**和**棋盘容量（§5.1b）。只改布防不改图，占格率仍是 32.7%，挤的感觉消不掉；只扩图不改布防，算子仍会堆在少数锚点上。
11. **地图放大 4 倍会把所有"每格成本"放大成卡顿（2026-10-12 实测，代价最大的教训）**：
    新图上线后单回合耗时 **1.06s → 79s**。根因不是"算子多"，而是四处每格/每次成本：
    - `_startPhase` 增援循环里**逐营调 `_supply()`**（每次全图 BFS）→ R3 单批 138 营 = 41.5s；
    - `_supply` 内 `Array.shift()` 是 O(n)，BFS 要访问 ~1.1 万格；
    - `findPath` 的开放列表**每轮 `open.sort()`** 是 O(n log n)，开放列表达数千项 → 单次 1410ms；
    - `inZOC` 每次重算邻居 → AI 一回合调 2 万次。
    **修完后 79s → 9.2s**。教训：**任何"每格/每次"的操作，在大图上都要重新量一遍**，
    别假设它还是原来的量级。相关红线注释已就地写进 `game.js`/`ai.js`，勿删。
12. **缓存要有失效钩子**：引入 `_zoc` 缓存后，所有改变单位位置的路径（`_setPos`/`_addUnit`/
    单位死亡与退出）都必须调 `_zocDirty()`。为此把散落的 `grid.delete(...)` 统一收敛到
    `_removeUnit(u)`。**用 `Get-Content -replace` 批量改写这类调用点时极易把参数写错**
    （本次就把 `_removeUnit(u)` 改成了 `_removeUnit(u.c, u.r)` 并造成自递归）——
    批量替换后必须 grep 复核每一处。
13. **`vertexColors: true` 会让没有顶点色属性的几何体渲染成纯黑（2026-10-12 实测）**：
    补给覆盖层最初整片发黑，原因就是给 `InstancedMesh` 的材质开了 `vertexColors: true`，
    而 `CircleGeometry` 没有 color 属性 → 顶点色按 0 相乘。**实例色只需 `setColorAt()`**
    （three 会自动启用 `USE_INSTANCING_COLOR`），材质保持 `color: 0xffffff` 且**不要**开
    `vertexColors`。同一坑在旧代码里也存在（`_hexMark` 的网格被判为黑），只是黑得"看起来像阴影"。
14. **城镇表重名会静默破坏 AI**：`mapgen.townMap` 以城镇名为键，重名后一座被另一座覆盖，
    而 `ai.js` 的 `germanTarget`/`usObjective` 正是按名取坐标。2026-10-12 就查出
    `讷沙托`、`迪基希` 各两座。**改 TOWNS 后必跑查重**（见 §5.3b）。
15. **六角形轮廓"配边"必须用几何最近邻，不能用方向角（2026-10-12 实测）**：
    `Hex.neighbors()` 返回的 6 个方向在奇偶行是两套不同偏移，与六角形顶点的
    奇偶排列顺序**不对应**。若按 `atan2(邻居方向)` 去匹配"边序号"，会配错边，
    轮廓碎成短线——实测 357 个端点中 266 个是断头、131 个碎环。
    改用"边中点 → 最近的邻居格中心"判定对侧后：**0 断头、1 条闭合环**。
    连续性可量化验收：**每个顶点度数恰为 2**（`qa/outline_check.js`）。

16. **加宽地图后，所有"带坐标的地理标签"必须一起重标（2026-10-13，本会话最大遗留问题）**：
    把 `COLS` 从 152 改成 220、把 `TOWNS` 按真实经纬度重算之后，我**忘了**
    `TERRAIN_RULES` 的 `cMin/cMax` 与 `ELEV_FEATURES` 的 `c/r` 也是地理标签。
    结果 12 个高程特征**11 个错位**（横向偏西 15~60 km），埃尔森博恩高地跑到了 90 km 之外，
    列日的马斯河谷消失了（轮廓长短轴比 6.60 → 1.36）。**校验全绿也发现不了**，
    因为断言里没有"地形是否对得上经纬度"这一项。
    **教训**：地图尺寸是"横纵坐标的容器"，改容器就必须把**所有以坐标表达的地理内容**
    一起过一遍——城镇、地形带、高程特征、河流、道路、出口线。改完用
    `qa/geo_align.js` 逐项核对（这个工具就是为此新增的）。

17. **"补覆盖"会诱导你造地名——必须设硬闸（2026-10-13）**：

18. **"就地正则批量改数据行"极易写坏字段（2026-10-13）**：

19. **PowerShell 会吃掉内联 node 脚本里的引号与 `$`（本会话反复中招）**：
    `node -e "…'中文'…"` 经常被 PowerShell 解析成别的意思（正则里的 `$1`、
    引号内的中文键名、`&&` 都会翻车），表现为莫名的 `SyntaxError` 或**静默改坏文件**。
    **规矩**：超过 3 行的脚本一律写成 `qa/_tmp.js` 再 `node qa/_tmp.js` 跑；
    用完删掉。同一坑还包括 `Set-Content -Encoding UTF8` 会给文件加 **BOM**，
    导致 `#!/usr/bin/env node` 这种首行直接语法错误——用 `fs.writeFileSync(P, s, 'utf8')`。

20. **`Object.assign` 的覆盖顺序 = 谁赢（2026-10-13）**：
    写 `Object.assign({}, BASE, packedUS, packedDE)` 时后写的赢；
    我写成 `Object.assign({}, SECTORS, dePacked, usPacked)`，结果美军打包表
    把德军结果**整体覆盖回旧值**，症状是"改了代码但分布没变"。
    **规矩**：多表合并时按"默认值 → 次要 → 主要"排，并打印合并后每张表的条目数与几行样本。

21. **`.length` 不是字节数（2026-10-13，一度误导排查）**：
    `build.js` 用 `(html.length/1024).toFixed(0)+'KB'` 报体积，而 `String.length` 是
    **UTF-16 码元数**；本项目中文极多，真实 UTF-8 字节比它大 ~30%
    （968,800 B 曾报成 "746KB"）。已改为 `Buffer.byteLength(html,'utf8')`。
    **规矩**：任何"文件多大"的判断都用 `Buffer.byteLength` 或 `fs.statSync().size`，
    不要用字符串长度；同理 `Content-Length` 与"字数"不是一个东西。

22. **把"地图之外"的城镇夹到边缘 = 真名假址（比假名更糟）（2026-10-13）**：

34. **手算 `行 = 20+(50.70-lat)×40.9` 极易漏 +20 或翻错符号（2026-10-24 反复中招）**：
    纬度高于 50.70 时括号内为负；本会话多次把 `(50.7-lat)×40.9` 忘加 20 而得出
    "表内错位 20 行"的假结论。**规矩**：换算一律走 `qa/geo_convert.js` 或脚本，
    快速心算锚点：纬度 50.0→r49、49.5→r69、49.0→r90；经度 0.1°≈5.1 列、0.5°≈25.6 列。
36. **生成器加新类型必须四处同步，漏 SUFFIX 会死循环（2026-10-24e）**：`mapType` 新增类型码后，`STATS`/`ORG`/`SUFFIX` 三张按类型索引的表与 `check_oob_big.js` 的 `TYPES_OK` 白名单必须同时补项——SUFFIX 缺项使缩写含 "undefined"，两个同型营缩写相撞时 `(base+k).slice(0,8)` 永不收敛 → 生成器静默死循环（无报错、无输出、CPU 满）。**规矩**：新增类型码后先 grep 全部按类型取值的表；跑生成器一律限时（spawnSync timeout），死循环秒级发现。
37. **本仓库 js 行尾混用（2026-10-24f 实踩）**：game.js/ai.js/ui.js 是 LF，render.js/index.html 是 CRLF——多行字符串锚点替换必须先查行尾（`s.includes(chr(13))`），LF 模式在 CRLF 文件上静默不命中；node -e 双层转义写 loader 这类长内嵌串必翻车，一律写临时脚本文件（§8-19 的加强版）。
36. **原版优化移植的适配点（2026-10-24f）**：原版 34 轮数值是逐行改 204 行 OOB，大阿登必须按【side+兵种+师名】写成 eliteStats 匹配器（1192 行，德美"第2装甲师"同名须按 side 分支）；原版 33④"入场格移进网内"在大阿登的对应问题是入场格落在**荒野留白区**——正解是"报到本师"锚定而不是就近网内硬搬（SS9 侦察营原格 [150,48] 本身就是货架伪坐标）。
35. **网络核查通道（2026-10-24 实测）**：本机 Bash 无外网（curl 超时）、WebFetch DNS 被污染
    （解析到假 IP）；可用通道是 **WebSearch**（经纬度查询很好用）和 **web_reader**
    （仅接受无查询参数的纯 ASCII 路径 URL）。批量核验城镇坐标用 WebSearch 单城单查。

38. **浏览器直载脚本的顶层 const 必须分片唯一（2026-10-24o 实踩）**：档案分片为 node/browser 双态各声明一个顶层数组（`const SHARD = [...]`）。node 下 require 各文件是独立模块作用域、同名无碍（全链校验绿）；但 build.js 把分片逐个**内联进同一全局作用域**，第二个 `const SHARD` 即 SyntaxError，该 <script> 块静默跳过——**表现是 QA 全绿而 dist 功能缺失**（档案只有 124/245 条）。规矩：浏览器直载脚本的顶层标识符一律带分片名后缀（SHARD_DE4/SHARD_US3/…）； dist 构建后必须在真实浏览器里核对全局挂载计数（本次用 `__DOSSIER_SHARDS.length` 抓出）。
39. **单文件版 boot 双 loader 竞态（2026-10-24o 实踩）**：build.js 把 vendor 标签替换为「threeGz 数据块 + 内联异步 loader（atob→DecompressionStream→THREE）」，但 index.html 原有的 vendor/CDN 回退 loader 仍在后面同步执行——它看到 THREE 尚未建立（解压还没完成）就误判失败去连 CDN（无网 3×6s 超时），随后派发 three-failed 把**已经成功**的启动状态覆盖成失败遮罩。修法：旧 loader 开头检测 `document.getElementById('threeGz')`，单文件版直接退出，加载与回退全权交给内联 loader。规矩：同一页面多个 loader 必须有明确的"谁负责"判定，异步加载器不能被同步兜底器抢先判死。
40. **脱敏只能作用于输出名，不能作用于匹配键（2026-10-28o 实踩）**：`gen_data_div.js` 里把 `deSensitize()` 同时套在「用 META.div 匹配 UNITS」这一步，导致 OOB 侧键已改名、META 侧仍存旧名 → 72 个师旅塌成 68 个且静默丢 4 个。规矩：**脱敏是展示层变换**——匹配用原值、写盘/显示用脱敏名；改完必须核对单位总数不变（师级 72/74、营级 1192 META）且 `希特勒/元首` 双零。
41. **"照片清理"要横扫四处，漏一处就等于没清（2026-10-28o 实踩）**：照片引用分散在 ① `vendor/photos/manifest.json`（构建内嵌清单）② `data.js` 的 `photo:` 直链（档案/简报/胜利画面）③ `dossiers_big_*.js` 档案条目的 `photo` 字段（**指挥部合集的 de5 是单行压缩 JSON，grep 中文名会漏，须按 `"side":"DE"` + `"photo":"http"` 匹配**）④ 图片说明 `photoCaption` 与 `credit`（即使图删了，说明里还写着"被俘美军"一样会被审核判问题）。规矩：清理后跑一遍统一正则复核（`希特勒|元首|Bundesarchiv|Captured_German|被俘美军|…`）对 **js 全目录 + 三张 html** 断言 0 命中，再 build。
42. **RAF 只能在主循环入口申请一次（2026-10-28p，最严重的性能事故）**：25j 加"渲染循环自愈"时把 `requestAnimationFrame(() => this._loop())` 放进 try 内，而入口本来已经有一份——每帧派生两条链，第 N 帧有 2^N 份回调，十几帧内主线程被同一场景的重复渲染压死（表现：开局几秒后越来越卡 → 完全卡死，CPU 100%）。**正确写法=入口申请一次、外面包整体 try/catch**。排查手法：`grep -c requestAnimationFrame` 与 `renderer.info.render.calls`（重复链会让 calls 每帧翻倍）。
43. **UI 启动链必须做浏览器冒烟，node 端 QA 覆盖不到（2026-10-28p 实踩）**：26f 加师级时把 `startGame` 的数据集分支写成"big/div 都先看 DATA_DIV"，营级剧本于是拿到没有 `big` 条目的数据集，`new Game` 读 `scen.fuelDE` 抛异常 → 点开始后无任何提示的卡死；而 check_big/div_check/ai_aggro 都在 node 里显式构造数据集，全绿。**规矩**：动过 `startGame` 的 DATA 切换、菜单或启动链，必须跑 `qa/_smoke_scen.js`（headless Chrome 逐个点开局，断言 units/errs），并检查 `window.__errs`。
44. **three.js 只 `scene.remove` 不 `dispose` 就是显存泄漏（2026-10-28p）**：行军箭头每次悬停重建、覆盖层每次选中重建、爆炸/曳光每次交火新建、阵亡算子整组网格——此前都只从场景移除。长时间推演后 GPU 内存只涨不降，帧率逐回合下滑。规矩：所有临时对象移除时 dispose geometry/material（材质带 `map` 连贴图一起 dispose），共享材质（`_hlMat`/`_hqMat`）必须排除，否则会连累其它算子。
